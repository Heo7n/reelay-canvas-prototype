## 为什么流程会把小改动放大

1. **定向入口不够定向。** `test:canvas` 执行 42 个文件，完整 legacy `test` 为 44 个文件，前者仍覆盖资产、主体、Agent、保存和撤销。`check:js` 还串行对全仓 JS 启动语法检查。微调时应先执行实际受影响的测试文件，不把 `check:canvas` 当成一个控件的小检查。
2. **同一轮重复准备。** `verify:shell` 重复执行 shell 类型检查；CI 的 `check → build:shell → build:experience` 又做三次。但它们总共仍只有约一分钟，削减这些秒级重复的优先级低于减少整轮人工重复验收。
3. **发布操作仍靠人工串联。** 脚本完成构建，CI 没有交付可直接部署的构建产物；发布时还需核对目录、目标项目、部署、域名及版本。内部持久站和外部体验站必须保留两个独立目标，不能为了省事混成一套产物。
4. **部分测试约束写法而非行为。** `tests/static-contracts.test.mjs` 存在函数字符串提取、局部变量和精确 CSS 数值断言。重命名或视觉尺寸调整会增加测试维护。后续改到这些区域时替换为有价值的行为验证，保留入口、协议和内容边界检查，不整体重写测试。
5. **视觉验收与发布次序交错。** PR #20 发布后又发现 iframe 行内基线导致 4px 外层滚动，随后 PR #21 单独重走发布。应先完成本轮受影响界面的视觉收口，再生成发布候选；非阻断的新发现进入下一明确切片。
6. **交接文档混有多轮历史。** `agent-handoff.md` 约 46 KiB，多段旧测试数、部署状态和切片记录并存。开始时按路由读取当前事实，历史证据查对应 PR；后续单独整理交接，避免每轮再复述整段历史。

## 下一轮怎么推进

以下为建议顺序，尚未作为代码改动实施：

1. **先缩短日常反馈循环。** 连续微调留在本 worktree，同一预览服务持续使用；每次只写清触发、反馈和需要保持的状态。视觉修改先看效果，再做相应行为复验；阶段完成才提交/发布。
2. **以对话或节点中的一个具体问题带动边界收敛。** 对话优先明确消息、草稿、任务与滚动归属；节点优先收拢编辑器生命周期。每次提取一个完整职责，并移除被替代路径，不同时保留两套实现。
3. **补少量可重复的浏览器关键流程。** 优先长提示词滚动与高级设置、节点多选/拖动/撤销、返回与重进项目、体验页刷新重置。先采用确定性内存数据，避免绑定真人账号和共享数据。当前没有这些可自动执行的 E2E，不能把计划写成已有覆盖。
4. **再统一发布入口。** 显式选择内部或体验目标，记录源提交、构建产物和部署，候选验收后提升同一部署。失败即停止，不重新生成数据或重新 seed。减少人的操作次数比继续压缩一分钟 CI 更重要。
